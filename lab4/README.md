## 2. Задание
Реализовать программу вычислений над матрицами с использованием блочного подхода. Провести эксперименты при различных размерах входных данных ($N$) и различных размерах блоков ($B_x \times B_y$).

## 3. Описание алгоритма и реализации

### 3.1. Проблема локальности данных
При классическом перемножении или обработке больших матриц процессор вынужден постоянно обращаться к оперативной памяти (RAM), которая работает значительно медленнее, чем кэш-память (L1/L2). Это приводит к частым "промахам кэша" (cache misses) и простаиванию процессора.

### 3.2. Блочная декомпозиция (Tiling)
Для решения этой проблемы применяется блочный алгоритм:
1. Матрица разбивается на небольшие блоки размером $B_x \times B_y$.
2. Вычисления производятся внутри каждого блока.
3. Данные одного блока загружаются в быстрый кэш L1/L2 и используются многократно, прежде чем процессор перейдет к следующему блоку.

Это значительно снижает количество обращений к медленной оперативной памяти.

### 3.3. Реализация
Программа выполняет операции над квадратными матрицами, используя вложенные циклы с шагом, равным размеру блока. Размер блока является варьируемым параметром эксперимента.

## 5. Анализ результатов

### 5.1. Влияние размера задачи
С увеличением размера матрицы $N$ время выполнения закономерно возрастает, что соответствует алгоритмической сложности задачи. Однако характер роста зависит от выбранного размера блока.

### 5.2. Влияние размера блока на производительность

1.  **Малые размеры ($N=200, 500$):**
    *   Наилучшие результаты показывает блок **$8\times8$**.
    *   *Причина:* При малых объемах данных накладные расходы на организацию циклов для крупных блоков превышают выгоду от кэширования. Кроме того, маленький блок целиком помещается в самый быстрый кэш L1, обеспечивая минимальные задержки.

2.  **Средние размеры ($N=1000$):**
    *   Оптимальным становится блок **$16\times16$**.
    *   *Причина:* Баланс между локальностью данных и накладными расходами. Блок $8\times8$ становится слишком мелким, и процессор тратит время на частую смену блоков, а $32\times32$ еще не дает существенного преимущества в кэшировании по сравнению с $16\times16$.

3.  **Большие размеры ($N=1500, 2000$):**
    *   Безоговорочный лидер — блок **$32\times32$**.
    *   *Причина:* При больших объемах данных критически важным становится сокращение обращений к RAM. Крупный блок $32\times32$ позволяет загрузить больше данных в кэш L2/L3 и использовать их многократно, прежде чем они будут вытеснены. Это drastically снижает количество cache misses.

### 5.3. Закон убывающей отдачи
Наблюдается, что после достижения оптимального размера блока дальнейшее его увеличение не всегда полезно. Например, для $N=2000$ блок $16\times16$ показал худший результат (0.168 сек), чем даже $8\times8$ (0.112 сек). Это может быть связано с особенностями выравнивания памяти или спецификой работы предвыборщика данных (prefetcher) процессора при данном размере шага.

## 6. Выводы

1.  **Критичность параметра блока:** Размер блока является ключевым фактором оптимизации производительности. Не существует универсального размера, подходящего для всех задач.
2.  **Зависимость от объема данных:**
    *   Для малых задач эффективны мелкие блоки ($8\times8$).
    *   Для средних — блоки среднего размера ($16\times16$).
    *   Для больших массивов данных необходимы крупные блоки ($32\times32$ и более) для эффективного использования иерархии памяти.
3.  **Эффективность блочного алгоритма:** Правильный подбор размера блока позволяет существенно ускорить выполнение программы (в некоторых случаях в разы) за счет улучшения локальности данных и снижения нагрузки на шину памяти.
4.  **Необходимость профилирования:** Для достижения максимальной производительности на конкретной аппаратной платформе необходимо проводить эмпирические тесты (как в данной работе) для выявления оптимального размера тайла.
